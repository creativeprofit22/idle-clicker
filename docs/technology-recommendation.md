# Technology recommendation

**Recommendation pending approval — researched 7 September 2026.**

Use **Godot 4.7.2 Standard, typed GDScript, the Compatibility renderer, and a small engine-native headless test runner**. Start with engine-native scenes and animation; do not add Rive, Blender, a database, or a third-party test framework to the opening-battle prototype. For later original artwork, use **Krita → PNG layers/frame sequences → Godot** as the minimal production pipeline.

This is a project-fit recommendation, not a benchmark result. Unity has the stronger ready-made cinematic sequencing workflow; Defold is a credible lean alternative with genuinely useful persistence and automation support. Godot provides the best balance here of native 2D authoring, low-cost tooling, directly editable project files, Android support without a .NET dependency, and tests running the same language and rules as the game.

The user explicitly authorized saving this report as the sole exception to `/research`'s read-only boundary. No engines, dependencies, repositories, game code, or tasks were installed, indexed, implemented, or created. Approval of this recommendation does not itself authorize those actions.

## Local baseline and decision criteria

The project is documentation-only: no engine manifest, executable game entry point, or test suite was found. Git history/status could not be inspected because the working directory is not a Git repository. There is no existing code investment favoring any engine.

The confirmed direction is an offline, single-player historical-armies idle game with polished **2D cinematic-anime presentation**, eventually on Android; the first prototype still uses placeholders. This latest direction resolves the older deferral of visual style. The gameplay brief calls for deterministic rounds, a rate-limited commander command, upgrades, defense, selective-retention resets, and saving/resuming frozen combat. The approved first-playable rules explicitly defer closed-app earnings; the earlier corpus handoff's references to bounded offline rewards overstate this slice. Those are mostly simulation and persistence problems, not physics or networking problems. Sources: `docs/game-design.md:3–5,21–27,33–53`; `docs/first-playable.md:3–5,21–47,76–103`; compare the earlier research brief in `docs/corpus-evidence.md:5–9`.

The decision weights are: a short code/test feedback loop for GG Coder; enough editor tools for the eventual presentation; predictable licensing; and an Android path that does not require optional native animation integrations. Corpus file counts are not a capability score. Direct upstream reads filled the GDScript/scene omissions and the failed Defold engine indexing recorded in `docs/corpus-evidence.md:11–23,25–43`.

## Why this recommendation, and why not the alternatives

**Godot fits the work rather than merely the prototype.** Its native animation and scene tools can remain in use after placeholders are replaced. GG Coder can keep combat in a typed GDScript object, independent of rendered nodes and elapsed wall time; a thin scene adapter supplies one round at a time and displays results. The same runtime executes tests and the actual battle, avoiding a separate Python/JavaScript implementation that could drift. Godot's Android documentation still labels C# support experimental, so choosing its Standard/GDScript build removes an avoidable .NET/export variable. The inspected corpus's C# examples are not a reason to choose C#. [Android guide, including C# warning](https://github.com/godotengine/godot-docs/blob/4.7/tutorials/export/exporting_for_android.rst#L14-L19)

**Unity is the runner-up for a different production shape, not an incapable or unaffordable option.** Its [Cinemachine/Timeline workflow](https://docs.unity3d.com/Packages/com.unity.cinemachine@3.1/manual/concept-timeline.html) explicitly activates, blends and cuts authored shots. Its [Test Framework](https://docs.unity3d.com/Packages/com.unity.test-framework@1.4/manual/reference-command-line.html) provides a fuller testing/reporting workflow than the tiny runner proposed here. We currently have neither an established Unity art team nor a large cinematic sequence requiring that workflow. The inference is that its editor/package/asset coordination and licensing administration would cost more than they save at this scope; no local timing benchmark establishes that. Reconsider only if the production team or a required asset/tool pipeline is substantially Unity-based. The indexed `Unity-Technologies/2d-techdemos` camera is merely basic target following, not the ceiling of Unity's camera capability: revision `6593d544df2ea598e51f5cf1d7165d5ed42ceba7`, [`Assets/Tilemap/IsometricZAsY/Scripts/BasicCameraFollow.cs:1–27`](https://github.com/Unity-Technologies/2d-techdemos/blob/6593d544df2ea598e51f5cf1d7165d5ed42ceba7/Assets/Tilemap/IsometricZAsY/Scripts/BasicCameraFollow.cs#L1-L27).

**Defold deserves a fairer comparison than the indexing failure suggested.** Directly read release-1.13.1 code has temporary-file serialization, checked writes/closes, rename-based replacement and error reporting in [`engine/script/src/script_sys.cpp:130–194`](https://github.com/defold/defold/blob/574678c7d44be490d874fbed2d0ae6211feec4d9/engine/script/src/script_sys.cpp#L130-L194); [`engine/script/src/test/scripts/test_sys.lua:75–105`](https://github.com/defold/defold/blob/574678c7d44be490d874fbed2d0ae6211feec4d9/engine/script/src/test/scripts/test_sys.lua#L75-L105) exercises saving, resaving and loading. This is better save-mechanism evidence than a tutorial's direct JSON overwrite, although it does not prove power-loss durability or our future schema/reset correctness. Its [1.13.1 release](https://defold.com/2026/08/17/Defold-1-13-1/) also adds lighting and editor automation capabilities. The reason not to choose it is the expected extra assembly of the layered, authored character/camera presentation, not an absence of shaders, Android, testing or local storage. No measured memory/package-size advantage has been established for this game.

## Presentation: supported mechanisms versus actual art work

Godot can support the target style with a small set of native systems. Use separate painted foreground/midground/background layers with `Parallax2D`; use `AnimatedSprite2D` for drawn frame sequences, or cutout parts with `Skeleton2D` and `AnimationPlayer` where reuse is appropriate. Key `Camera2D` position/zoom, sprite transforms, color and opacity with `AnimationPlayer`; introduce `AnimationTree` only when transitions require it. Keep command resolution authoritative in the simulation: an animation event must not decide whether damage happened. [Parallax2D](https://github.com/godotengine/godot/blob/4.7.2-stable/doc/classes/Parallax2D.xml) · [AnimationPlayer](https://github.com/godotengine/godot/blob/4.7.2-stable/doc/classes/AnimationPlayer.xml) · [AnimationTree](https://github.com/godotengine/godot/blob/4.7.2-stable/doc/classes/AnimationTree.xml) · [Camera2D](https://github.com/godotengine/godot/blob/4.7.2-stable/doc/classes/Camera2D.xml)

This is supported by actual, previously unindexed scene/code reads from `godotengine/godot-demo-projects`, revision `0db80ca5fd22b9a40e05b9bc1e00af867fb7c712`: [`2d/skeleton/player/player.gd`](https://github.com/godotengine/godot-demo-projects/blob/0db80ca5fd22b9a40e05b9bc1e00af867fb7c712/2d/skeleton/player/player.gd) switches idle/run animation; [`player.tscn`](https://github.com/godotengine/godot-demo-projects/blob/0db80ca5fd22b9a40e05b9bc1e00af867fb7c712/2d/skeleton/player/player.tscn) contains keyed tracks and a skeletal scene; [`level/parallax_background.tscn`](https://github.com/godotengine/godot-demo-projects/blob/0db80ca5fd22b9a40e05b9bc1e00af867fb7c712/2d/skeleton/level/parallax_background.tscn) shows layered scrolling. Some sample nodes are older patterns; prefer the current version's native APIs over copying a whole demo. Corpus search/show also confirmed simple sprite variation in [`mono/dodge_the_creeps/Mob.cs:1–13`](https://github.com/godotengine/godot-demo-projects/blob/0db80ca5fd22b9a40e05b9bc1e00af867fb7c712/mono/dodge_the_creeps/Mob.cs#L1-L13), which is mechanism evidence, not an anime visual reference.

For effects, start with native 2D particles and simple canvas-item hit-flash/distortion materials, not a full-screen post-processing stack. Godot documents both [GPU particles](https://github.com/godotengine/godot/blob/4.7.2-stable/doc/classes/GPUParticles2D.xml) and a [CPU alternative](https://github.com/godotengine/godot/blob/4.7.2-stable/doc/classes/CPUParticles2D.xml); GPU-feature availability still depends on renderer/device. Build touch UI with native [Control layout](https://github.com/godotengine/godot/blob/4.7.2-stable/doc/classes/Control.xml), readable labels, an explicit commander button, adequate touch targets and safe-area-aware layout. [Screen-touch events](https://github.com/godotengine/godot/blob/4.7.2-stable/doc/classes/InputEventScreenTouch.xml) carry touch identity; do not count a physical touch and its emulated mouse event as two commands.

Unity offers equivalent building blocks with stronger integrated camera sequencing; Defold documents [flipbooks/property animation](https://defold.com/manuals/animation/) and [GUI authoring](https://defold.com/manuals/gui/), and supports shader/render customization. The comparative judgment is about authoring effort, not whether those engines can draw anime art.

**None of this creates the style automatically.** Character design, clean silhouettes, historical reference interpretation, linework, backgrounds, poses, anticipation, impact frames, compositing, shot timing, sound and coherent direction remain artist/animator work. GG Coder can wire assets, author simple timing curves and automate exports/tests; headless success cannot approve composition, animation quality, readability or emotional effect. Editor preview and human visual decisions remain necessary in all three engines. No inspected demo's art is proposed as production content; licenses for each borrowed asset must be checked separately from repository code licenses.

## Minimal asset pipeline; Rive and Blender are optional, different tools

**Baseline: Krita and Godot only when art production begins.** Keep editable layered drawings in Krita; export named transparent PNG layers and short frame sequences; assemble/import them using Godot's native sprite and animation tools. Agree on pivots, scale, framing and naming before producing many assets. Krita's [render documentation](https://docs.krita.org/en/reference_manual/render_animation.html) describes image-sequence/PNG output. Its [license](https://krita.org/en/about/license/) permits commercial art and does not impose the application's GPL on that art. Use the free direct-distribution application; paid storefront distribution is optional. No art application is required for the placeholder battle.

**Rive is an optional interactive-animation runtime plus a separate authoring service.** It might later help a vector-heavy HUD or animated reward badge; it is not required for drawn character animation or camera sequencing. Current Rive pricing lists runtime export on Cadet at **US$17/seat/month or US$108/seat/year**, with Free lacking that production-export entitlement. Voyager is **US$39/month or US$304/year** per seat. The inspected [Unity runtime license](https://github.com/rive-app/rive-unity/blob/main/LICENSE) and [core runtime license](https://github.com/rive-app/rive-runtime/blob/master/LICENSE) are MIT; runtime-code licensing is distinct from editor-export pricing and asset licenses. [Rive pricing](https://rive.app/docs/account-admin/pricing)

Actual integration support differs sharply. Rive's [Unity documentation](https://rive.app/docs/game-runtimes/unity/unity) supports Unity LTS 2021 onward, including Unity 6, and lists Android OpenGL/Vulkan rendering. Defold has an [official extension](https://defold.com/extension-rive/), with native integration confirmed in `defold/extension-rive` revision `22be59a370162c0df8b6c44fcaff1e28d3e864ef`, [`defold-rive/commonsrc/file.cpp:365–445`](https://github.com/defold/extension-rive/blob/22be59a370162c0df8b6c44fcaff1e28d3e864ef/defold-rive/commonsrc/file.cpp#L365-L445). Its [README](https://github.com/defold/extension-rive/blob/22be59a370162c0df8b6c44fcaff1e28d3e864ef/README.md) excludes Android armv7; its official documentation specifies additional OpenGL/Vulkan requirements. That restriction belongs to the extension, not all Defold games.

For Godot, the inspected [gjonn/godot-rive integration](https://github.com/gjonn/godot-rive/blob/main/README.md) reports tested Godot 4.7.2/macOS support but no native Windows/Linux/Android binaries. [RiveGD](https://github.com/maidopi-usagi/RiveGD/blob/main/README.md) reports Android/iOS untested and explicitly warns against production use. These are community projects, not proof of a supported Godot Android production route. This is a concrete reason to omit Rive from the recommended stack now; it is not a claim that a future integration is impossible.

**Blender is optional authoring/rendering software, not the equivalent of Rive's game runtime.** It can produce pre-rendered architecture, perspective guides, effects or animated sprites when 3D staging saves artist time. Export transparent PNG frame sequences and use the same Godot sprite pipeline; no Blender runtime ships to Android. Blender's [render manual](https://docs.blender.org/manual/en/latest/render/output/animation.html) recommends frame sequences for recoverable rendering workflows, and its [GPL explanation](https://docs.blender.org/manual/en/latest/getting_started/about/license.html) explicitly excludes generated artwork from the application's GPL obligations. Blender itself has no required subscription; asset/add-on terms are separate.

Godot does have a real `.blend` importer, but it is an editor-side dependency, not magic universal interchange. Inspected [`modules/gltf/editor/editor_scene_importer_blend.cpp`](https://github.com/godotengine/godot/blob/4.7.2-stable/modules/gltf/editor/editor_scene_importer_blend.cpp) locates and executes Blender and checks its version. The baseline avoids that workstation dependency by accepting exported images. Blender and Rive therefore remain optional for different needs, neither a mandatory production purchase nor a substitute for animation labor.

## Android, persistence and performance risks

All three engines can produce an offline game; online accounts, analytics, remote assets and build-service dependencies are separate choices. Do not add gameplay networking merely because a sample has it. Build-time downloads and store distribution are different from an offline runtime.

Godot's [4.7 Android instructions](https://github.com/godotengine/godot-docs/blob/4.7/tutorials/export/exporting_for_android.rst) describe desktop setup with OpenJDK 17, Android SDK components, matched export templates, Gradle for AAB, and non-debug signing for store uploads. Unity supplies Android build support as an editor module; its [requirements](https://docs.unity3d.com/6000.6/Documentation/Manual/android-requirements-and-compatibility.html) and chosen editor's tool versions must match. Defold's [Android guide](https://defold.com/manuals/android/) and [Bob CLI](https://defold.com/manuals/bob/) support APK/AAB bundling; current Bob documentation requires OpenJDK 25. Android export is documented, not verified on this machine. Google Play's target-API/native-library/signing requirements must be rechecked at release time rather than inferred from the presence of an export button.

**Lifecycle and saving require explicit application rules in every engine.** Godot's [pause guidance](https://github.com/godotengine/godot-docs/blob/4.7/tutorials/inputs/handling_quit_requests.rst#L55-L69) notes that a suspended Android app can be killed without a later shutdown opportunity. Unity exposes [pause callbacks](https://docs.unity3d.com/6000.6/Documentation/ScriptReference/MonoBehaviour.OnApplicationPause.html), with Android keyboard/focus caveats. Defold exposes [focus/window callbacks](https://defold.com/ref/stable/window-lua/). Save on meaningful state transitions and suspension, not solely on quit. For the approved first-playable rules, resume must preserve the saved round and fractional progress, without awarding closed-app rewards or replaying missed frames as combat.

Godot's [`user://`](https://github.com/godotengine/godot-docs/blob/4.7/tutorials/io/data_paths.rst#L59-L68), Unity's [`persistentDataPath`](https://docs.unity3d.com/6000.6/Documentation/ScriptReference/Application-persistentDataPath.html), and Defold's save APIs provide locations/mechanisms, not our schema validation, backups, reset transactions or duplicate-outcome prevention. Later persistence work must preserve a last-known-good save, check write/replace failures, validate versions/ranges, and avoid acknowledging a saved outcome or reset before durable state is accepted. Local storage can still be removed by clearing app data or uninstalling; offline-only is not a cloud backup promise. Those requirements belong to later approved work, not this opening-battle slice.

Two reference reads illustrate the distinction. Godot's [JSON serialization demo](https://github.com/godotengine/godot-demo-projects/blob/0db80ca5fd22b9a40e05b9bc1e00af867fb7c712/loading/serialization/save_load_json.gd) directly opens a save for writing; it is not a crash-safe persistence template. `pmotschmann/Evolve` revision `3436358dcd03d9f9e071d51ea071e0a78c0322e4`, [`src/resets.js:1–88`](https://github.com/pmotschmann/Evolve/blob/3436358dcd03d9f9e071d51ea071e0a78c0322e4/src/resets.js#L1-L88), shows backup/prestige/reset ordering but also browser reload/analytics assumptions we should not copy. Neither source proves this project's future save behavior.

**Start with Compatibility rendering, not Forward+.** Godot's [renderer guide](https://github.com/godotengine/godot-docs/blob/4.7/tutorials/rendering/renderers.rst) explicitly positions Compatibility for broad/older-device support and 2D without advanced features. That is a reasonable default, not a measured victory over Mobile. Revisit only if a required effect cannot fit the chosen renderer and target-device testing justifies the switch.

The likely Android limits are transparent-layer overdraw, large texture/frame-sequence memory, full-screen effects, particles, draw-call/material churn, loading stalls and sustained thermal/battery cost—not the arithmetic of a few squads. One uncompressed 4096×4096 RGBA8 texture is **64 MiB before mipmaps** (calculated, not a runtime measurement). Use short reusable animation loops, sensible texture sizes/atlases, limited overlapping effects and event-driven UI updates. Keep the one-second logical battle clock separate from visual refresh; freeze rather than simulate combat while suspended. Actual frame time, memory, startup, battery and package size remain unmeasured. A named low-end Android target and eventual on-device tests are required before making performance promises; the first placeholder slice cannot validate the final art load.

## Test setup and only the first implementation slice

**Proposed test setup:** a tiny GDScript `SceneTree` runner invoking the actual combat model, printing named failures and a pass count, and calling `quit(1)` on failure or `quit(0)` on complete success. This is not a claim that Godot includes a full application-unit-test framework. It is the minimum setup for two deterministic cases, with no plugin compatibility or package-install work. Do not rely only on a logged error or an `assert` stopping one function; the eventual verification must include an intentionally failing expectation to prove the process reports failure. Grow into an established test framework only when the suite needs fixtures/reporting that justify one.

The prospective invocation is `godot --headless --path . --script tests/run_tests.gd`, using the installed console executable's actual path when available. Godot documents [`--headless`](https://github.com/godotengine/godot-docs/blob/4.7/tutorials/editor/command_line_tutorial.rst#L119-L120), [`--script`](https://github.com/godotengine/godot-docs/blob/4.7/tutorials/editor/command_line_tutorial.rst#L234-L239) and [`SceneTree.quit(exit_code)`](https://github.com/godotengine/godot/blob/4.7.2-stable/doc/classes/SceneTree.xml#L202-L207). This command was **not run**: no runnable game project or Godot executable was established locally. Unity's fuller Test Framework can run EditMode/PlayMode tests from a batch command and produce NUnit XML; Defold's Bob builds are not automatically Lua gameplay tests. Direct Defold [AndroidBundlerTest.java](https://github.com/defold/defold/blob/574678c7d44be490d874fbed2d0ae6211feec4d9/com.dynamo.cr/com.dynamo.cr.bob.test/src/com/dynamo/bob/bundle/test/AndroidBundlerTest.java) reads confirm engine packaging assertions, not battle-rule coverage.

After separate implementation authorization, build **one placeholder opening battle**, not three prototypes:

1. Create one Godot Standard/Compatibility project, one battle scene, one plain typed combat model and the minimal test entry point. No generic combat framework, dependency-injection layer, inventory or content pipeline is necessary.
2. Show three labeled player squad placeholders, one enemy shield placeholder, health/round information, one commander button and a terminal victory state. Supply automatic one-second rounds while foregrounded. The scene and tests call the same round-step/command path; the tests advance rounds directly without waiting real seconds.
3. Preserve the opening rules: player health **120/40/60**, damage **4/8/6**; enemy shield health **72**, damage **3**. A commander strike adds **6** damage. All attacks use round-start state and apply simultaneously, so the enemy attacks even in its death round. Repeated commands within an interval accept only one; nothing damages either side before the first boundary.
4. Prove the two outcomes below, including no earlier victory and each surviving squad’s exact remaining health. Freeze the result instead of auto-entering level 2. Do a small visible smoke check of the same scene when the engine is available; a headless arithmetic test does not prove touch layout or rendering.

| Required regression | Exact expected observations |
| --- | --- |
| Passive opening victory | Damage 18/round; enemy health **54, 36, 18, 0**; shield health **117, 114, 111, 108**. Ongoing after round 3; victory exactly after round 4. Player archers remain 40 and horse archers 60. |
| Commander-assisted opening victory | One accepted strike in each interval; damage 24/round; enemy health **48, 24, 0**; shield health **117, 114, 111**. Ongoing after round 2; victory exactly after round 3. Other squads remain 40 and 60. Repeated taps in an interval must not shorten this. |

These expected values were checked by arithmetic against `docs/first-playable.md:25–29,39–47,59–61,109–111`; they are **not passing gameplay tests**. The slice excludes other encounters, farming, upgrades, economy, defense, saves/offline rewards, prestige, final art, Rive/Blender, Android packaging, store work and performance benchmarking. Persistence and production concerns above explain engine suitability and future risks; they are not extra implementation steps.

## Approval boundary and remaining uncertainty

Approve or reject **one direction: Godot 4.7.2 Standard + typed GDScript + native headless tests, with engine-native animation and later Krita PNG assets**. The immediate work remains blocked pending that recommendation decision and separate implementation authorization.

No local runtime comparison, test execution, visual review or Android measurement was possible with the established tools. Remaining risks are the cost/availability of original cinematic-anime art, renderer/texture budgets on the eventual Android target, unimplemented reliable saves and lifecycle behavior, the deliberately minimal test runner's future scaling limit, and tool-version/store requirements at shipping time. Those uncertainties do not justify three competing prototypes; they require focused checks on the chosen stack when those stages are actually approved.
